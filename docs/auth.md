# Authentication and identity

Binding rules: spine AD-6 to AD-10. This page explains how they fit together.

## Access tokens

- A **JWT**, signed by auth-api with an **RS256 private key** that only auth-api holds. It lives **15 minutes**.
- auth-api publishes the matching **public key** at `/.well-known/jwks.json`, plus a small discovery document at `/.well-known/openid-configuration` (`issuer`, `jwks_uri`) that the standard .NET JwtBearer handler reads. Both are internal-network only. A public key can verify signatures but can't create them.
- Every service (not the gateway) validates tokens **locally**: signature, `iss=mycollection-auth`, `aud=mycollection`, expiry. The setup lives once in `libs/MyCollection.ServiceDefaults`: `MetadataAddress` comes from `Jwt__MetadataUrl`, with `RequireHttpsMetadata=false` (internal network) and `MapInboundClaims=false`. Services fetch the keys over the internal Docker network and cache them.
- Claims: `sub` (user id, UUIDv7, lower-case), `name`, `email`, `iat`, `exp`, `jti`. The header carries `kid` (the key's RFC 7638 thumbprint). No roles yet.
- **The acting user is always `ICurrentUser.Id`** (parsed from `sub`). Never trust a user id from the body, route or query string.
- Access tokens can't be revoked: after logout, one stays valid until it expires (at most 15 min).

| Holder | Key | Can |
|---|---|---|
| auth-api | private key (+ public) | sign tokens |
| other services | public key (from JWKS) | verify only |
| gateway, browser | none | pass tokens along / read claims |

The only secret here is the private key: a PEM generated by a `tools/` script and mounted into auth-api. It is never committed.

## Refresh tokens

- An **opaque random string** (not a JWT), stored **only as a SHA-256 hash** in `refresh_tokens (id, user_id, family_id, token_hash, replaced_by_id, family_expires_at, expires_at, consumed_at, revoked_at)`.
- Lifetime is **30 days, sliding**: each refresh issues a new token with a fresh 30 days, never past the family's **90-day absolute cap**. After that the user logs in again.
- **Rotation:** each `POST /api/auth/refresh-token` consumes the current token with one atomic conditional `UPDATE` and inserts its successor in the same transaction, in the same *family*.
- **Reuse detection:** if a consumed token comes back
  - **within 10 s**, it's a multi-tab race, so a **new sibling token** in the same family is issued (the original successor can't be returned, because raw tokens are never stored);
  - **after 10 s**, it's treated as theft, so the **whole family is revoked** and the response is `401 refresh_token_reused`.
- **Logout** needs only the refresh cookie and revokes its family.
- All time comes from the injected `TimeProvider`, so tests can control the clock.

## How tokens reach the browser

- The **refresh token** goes only in the cookie `refresh_token`: `HttpOnly; Secure; SameSite=Strict; Path=/api/auth`. JavaScript can't read it.
- The **access token** goes only in the JSON body. The frontend keeps it **in memory**.
- **On page load**, the frontend calls `POST /api/auth/refresh-token` (with `credentials: 'include'`), called a *silent refresh*. If the cookie is valid, the user is logged in.
- **OAuth (Google/Discord), one flow for every provider (AD-22):**
  1. The browser opens `/api/auth/<provider>`, which redirects to the provider.
  2. The provider sends the browser back to `/api/auth/<provider>/callback`, which the ASP.NET handler owns. The handler stores the result in a short-lived `ext_auth` cookie (`SameSite=Lax`, 5 min).
  3. The handler redirects to `/api/auth/<provider>/complete`, which applies the linking rules, sets the refresh cookie, deletes `ext_auth`, and `302`s to `Frontend__AuthCallbackUrl` (with `?error=<code>` on failure).
  4. The frontend does the silent refresh.
  - No token ever appears in a URL, and redirect targets come only from config.
- Every token-issuing response has the same shape: `{ accessToken, expiresAt }`.
- The gateway's CORS allows credentials only for allow-listed origins (dev: `http://localhost:5173`).
- The web UI must be served from the **same site** as the gateway (`localhost` in dev; the same registrable domain in production), or `SameSite=Strict` blocks the cookie.
- In dev, `http://localhost` counts as a secure context in **Chrome, Edge and Firefox**, so `Secure` cookies work without HTTPS. **Safari** drops them over HTTP; it needs HTTPS, which comes later with TLS.

## Account linking

| Situation | Result |
|---|---|
| Password registration | Account created, `email_verified_at` = null (no email verification yet) |
| Google/Discord login, provider email **unverified** (or the verified flag is missing) | **Refused** |
| Google/Discord login, verified email, no existing user | New user, `email_verified_at` set |
| Google/Discord login, verified email matches a **verified** user (e.g. signed up with the other provider) | **Linked** to that user |
| Google/Discord login, verified email matches an **unverified** password account | **Refused** (prevents account takeover) |

- Emails are trimmed and lower-cased before they are stored or compared.
- Provider access tokens are **discarded** after login. `user_oauth` stores only `(id, user_id, provider, provider_user_id, email, linked_at)`.
- Passwords are bcrypt-hashed in `user_credentials`.
- **Accepted gap:** email squatting via password registration, until the `spec-email-identity` spec adds verification and password reset.
