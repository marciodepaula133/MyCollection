- (direction) Source: 8016d993-cf28-492a-9c3c-aa943891c8c6.md (PT-BR architecture notes). User: monorepo; current scope only Auth API + gateway.
- (decision) Slug mycollection-platform: one spec for the whole product; Wishlist and Cards BFF join it later.
- (decision) Why = both: a real card-collection tool the user wants AND a portfolio/interview piece demonstrating microservices, auth, BFF, caching, infra.
- (decision) Social login (Google + Discord) is in the first Auth API scope, overriding roadmap phase 5 ordering.
- (decision) Where JWT gets validated (gateway vs services) deferred to bmad-architecture; logged as open question.
- (capability) CAP-1 Register with email/password. success: POST register creates user; duplicate email rejected; password stored only as bcrypt hash.
- (capability) CAP-2 Login with email/password returns short-lived access JWT + long-lived refresh token. success: valid creds -> tokens; invalid creds -> 401 without revealing which field was wrong.
- (capability) CAP-3 Renew session with refresh token. success: valid refresh token -> new access token; expired/revoked refresh token rejected.
- (capability) CAP-4 Logout invalidates refresh token. success: refresh with a logged-out token fails.
- (capability) CAP-5 Sign in with Google (OAuth2/OIDC). success: redirect -> callback -> JWTs issued; first login creates user, later logins reuse the same user.
- (capability) CAP-6 Sign in with Discord (OAuth2). success: same flow/outcome as CAP-5 for Discord.
- (capability) CAP-7 Gateway is the single public entry: routes /api/auth/* to Auth API, applies CORS, global rate limiting, request logging. success: frontend reaches auth only via gateway; service ports not needed by clients; over-limit returns 429; disallowed origin blocked.
- (capability) CAP-8 One-command local environment. success: docker compose -f docker-compose.dev.yml up brings up gateway, Auth API, Postgres; editing a .cs file hot-reloads without rebuild.
- (constraint) Monorepo: all services, gateway config and compose files in one repository.
- (constraint) Services are .NET; Auth API persists in PostgreSQL (users, user_credentials, user_oauth split per notes).
- (constraint) Gateway is Nginx.
- (constraint) Passwords never stored in plain text (bcrypt).
- (constraint) Access token short-lived, refresh token long-lived.
- (constraint) Future services (Wishlist on MongoDB, Cards BFF on Redis + external APIs) must be addable to the monorepo and gateway without restructuring.
- (constraint) Secrets (JWT secret, OAuth client secrets) come from environment config, not source code.
- (decision) Non-goals now: Wishlist Service, Cards BFF, Redis, MongoDB, frontend, production deployment/hosting, observability beyond request logs + health (roadmap phase 6).
- (assumption) Social login matching: a social login whose provider email equals an existing user's email links to that user rather than creating a duplicate — needs confirmation.
- (question) Where is JWT validated: in Nginx (auth_request / njs) or in each service?
- (question) Account linking: should Google/Discord login with an email already registered via password link to that account automatically?
- (question) Token lifetimes (access, refresh) and whether refresh tokens rotate on use?
- (question) Are the OAuth provider access tokens needed later (notes store access_token in user_oauth) or can they be discarded after login?
- (question) Supported card games (Magic only via Scryfall, or also Pokemon etc.)? Not blocking current slice.
