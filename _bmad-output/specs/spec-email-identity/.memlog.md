Scope: phase 2 of spec-mycollection-platform, auth-api only — email verification, unconfirmed-account handling, password reset, social-account takeover.
- (constraint) Inherited from spine: SMTP via MailKit; Brevo as production SMTP relay (~9000/month free); Mailpit in dev; email templates are HTML built in C# application code, sent as the SMTP body — never the provider's dashboard template editor, so the relay stays swappable via SMTP host/credentials alone.
- (constraint) Inherited from spine AD-10/AD-11: emails trimmed+lower-cased before store/compare; users.email unique; users.email_verified_at already exists as a column, set today only from a provider-asserted verified social login. Password-registered accounts are unverified from birth. This spec closes AD-10's accepted gap: email squatting via password registration (a squatter registers a victim's real email first, blocking the victim's later legitimate registration/social login).
- (constraint) Hexagonal/Result<T>/ProblemDetails/snake_case error code conventions (AD-2, AD-13) and the Auth.Domain/Application/Infrastructure/Api split apply to every capability below, same as phase 1.
- (capability) CAP-9 Send verification email on registration. Intent: a newly password-registered user receives an email with a link/token to confirm their address. Success: registration triggers exactly one verification email to the registered address; the token identifies the user and expires.
- (capability) CAP-10 Confirm email. Intent: a user follows the verification link and their account becomes verified. Success: a valid, unexpired token sets email_verified_at; the same token cannot be reused; an expired or invalid token is rejected with a clear error, not a 500.
- (capability) CAP-11 Resend verification email. Intent: an unconfirmed user can request the verification email again if it was lost or expired. Success: a new email is sent and any prior outstanding verification token for that user is invalidated; already-verified accounts get a no-op response, not a new email.
- (capability) CAP-12 Request password reset. Intent: a user who forgot their password requests a reset email by submitting their address. Success: if the address belongs to a password account, a reset email is sent; the response is identical whether or not the address exists, so the endpoint never reveals which emails are registered.
- (capability) CAP-13 Confirm password reset. Intent: a user sets a new password using the token from the reset email. Success: a valid, unexpired, unused token lets the user set a new bcrypt-hashed password; the token cannot be reused; all of the user's existing refresh-token families are revoked, forcing re-login everywhere; an expired/invalid/reused token is rejected.
- (capability) CAP-14 Close the email-squatting gap: verified social login reclaims a squatted, still-unverified password account. Intent: when a social login with a provider-verified email matches an existing UNVERIFIED password account, the legitimate owner (proven via the provider's verified email) takes over — instead of AD-10's current 'refused'. Success: after reclaim, the social identity is linked to the (now-verified) account and the account is usable via that social login; the squatter's password credential on that account no longer grants access to it.
- (assumption) CAP-14's reclaim mechanism (verified social login evicts the squatter's password credential rather than merging accounts or requiring extra confirmation) is a best-effort distillation, not an explicit spine/memlog decision. Flagged as open_questions rather than treated as settled.
- (question) CAP-14 mechanics: on reclaim, is the squatter's password credential deleted outright (account becomes social-only), or kept and just superseded so the rightful owner can still set a password later? Does reclaim happen automatically on OAuth /complete, or does it require one extra explicit confirmation step (higher-friction but safer against a stolen OAuth session)? What happens to any data the squatter created under that account (wishlist, etc. in later slices)?
- (question) Do unconfirmed password accounts get any login restriction (spine/CAP-2 today allows login regardless of email_verified_at), or does phase 2 introduce a restriction (e.g. blocked from sensitive actions, or blocked from login entirely until confirmed)? Not decided in the spine.
- (question) Should long-unconfirmed password registrations eventually expire/free up the email (so a squatter who never confirms doesn't block the real owner forever), or does CAP-14's social-login reclaim remain the only way out? Not decided in the spine.
- (constraint) Verification and reset tokens are opaque, single-use and time-limited, following the same 'never store the raw secret' posture as AD-8 refresh tokens (store a hash, not the token). Exact TTLs and token format are HOW, deferred to architecture, not fixed here (Spec Law rule 2).
- (note) CAP-13 (password reset) revoking all refresh-token families is a security best-practice default (matches AD-8 machinery already in place) applied without needing new user confirmation — logged as a decision, not an open question, since it directly extends an existing binding rule (AD-8) rather than inventing new mechanism.
- (direction) Non-goals for this slice: changing an already-verified account's email address; admin/manual account merge tooling; SMS or other non-email channels; production TLS/hosting (spine Deferred, unrelated); rate-limiting specifics beyond the gateway's existing global+auth limits (AD-14, already covers /api/auth/*).

- (decision) CAP-15 (new): unconfirmed password accounts are blocked from login entirely until confirmed, not just restricted in what they can do. Login attempt returns a stable error code (e.g. email_not_verified), not a generic invalid_credentials. Resolves prior open question.
- (decision) CAP-14 mechanics resolved: on reclaim, the squatter's password credential (user_credentials row) is deleted outright, not superseded/kept -- the account becomes social-only immediately. Reasoning: unlike normal verified<->verified linking where both credentials genuinely belong to the same real owner, the squatter's password was set by someone never proven to own that email; leaving it valid would let the squatter log back into the reclaimed account, defeating the point of reclaim. Reclaim happens automatically inline during OAuth /complete (same flow as a normal social sign-in), no extra confirmation screen. User confirmed both.
- (decision) Unconfirmed password registrations expire after 1 month: if email_verified_at is still null 30 days after registration, the registration is freed (email becomes available again for a fresh password registration or an unimpeded social login/reclaim). CAP-11 (resend verification) remains available any time before expiry. This is a second, independent path to close the squatting gap alongside CAP-14 -- CAP-14 handles reclaim via a rightful owner's social login before 30 days; this handles the case where nobody ever reclaims it.
